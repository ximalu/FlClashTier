# FlClashTier 开发纪要

> 本文件归档 FlClashTier 项目全部讨论内容（2026-08-13 定稿）。
> 源码级验证细节见 `~/.hermes/skills/software-development/flclashtier/references/source-analysis.md` 与 Hermes skill `flclashtier`。

## 一、项目定位

> 不是"把 ZeroTier 和 Mihomo 两个 App 合并"，而是"在一个 Android VpnService 中，将 ZeroTier Core 和 Mihomo Core 作为两个并列的网络出口"。

- ZeroTier 管私网（ZT managed routes 网段，如 192.168.191.0/24）
- Mihomo 管代理/公网（DIRECT / PROXY）
- 唯一需要自己创造的新东西：**Pump**（TUN 数据分流层）
- 用户动机：个人执念 + 学习项目（非必需工具，已有 VPS 跳板 + frp 覆盖需求）

## 二、M0 架构定稿（2026-08-13）

**结论：M0 不需要修改 Mihomo，不需要修改 Android VpnService，不需要增加 JNI；只需要在 `tun.Start()` 与 `sing_tun.New()` 之间插入一个 packet pump。**

### 正向数据流

```
Android VpnService
      │  real TUN fd
      ▼
┌───────────┐
│ ZT Pump   │
└─────┬─────┘
      │  SOCK_DGRAM socketpair
      ▼
sing_tun / Mihomo
      │
      ▼
    Proxy
```

### 反向数据流

```
Mihomo
      │
      ▼
socketpair
      │
      ▼
ZT Pump
      │
      ▼
real TUN fd
```

### M0 的本质

> M0 的本质甚至不是"改造 Mihomo"。
> 而是：**把 Mihomo 原来直接拿到的 TUN fd 换成一个行为上足够像 TUN 的 Unix DGRAM fd。**

## 三、关键技术决策：为什么 SOCK_DGRAM

已验证：

- TUN → 一次 read → 一个 packet
- SOCK_DGRAM → 一次 recv/read → 一个 datagram

语义非常接近：

```
真实 TUN            SOCK_DGRAM
   │                   │
   │ packet            │ datagram
   ▼                   ▼
  pump  ──────────►  socketpair  ──►  sing_tun
```

不会像 SOCK_STREAM 那样需要自己处理 framing 问题（packet A 被拆成 A 的一半 + A 另一半 + B 的一部分……）。

**这是 A 路线（泵替换）非常适合本项目 PoC 架构的根本原因。**

### 已验证的源码依据（M0 前提）

数据通路 100% 只 read/write，唯一 ioctl 失败也不致命：

1. `sing-tun New()` (tun_linux.go L53-89)：FileDescriptor != 0 时跳过 open+TUNSETIFF（L118），直接 os.NewFile 包装，零 ioctl
2. GSO 不触发：FlClash LC.Tun 无 GSO 字段；即使开启，Android fd 无 VNET_HDR → enableGSO 直接 return error → New() 仅 Warn
3. gvisor 栈 (tun_linux_gvisor.go → fdbased)：唯一 fd 操作 SetNonblock + epoll + readv/writev，零 ioctl（fdbased 注释 "works with all kinds of FDs"）
4. system 栈：纯 tunFile.Read/Write
5. mihomo 唯一 ioctl：getTunnelName 用 TUNGETIFF，socketpair 上返回 ENOTTY → 仅 Warn + fallback 接口名，不阻断启动

**预期会看到的 Warn**：`[TUN] get tun name failed for fd X, fallback to use tun interface name FlClash` — 正常现象，不是失败。

## 四、M0 实验建议：零 ZeroTier

强烈建议第一版代码不要同时加入 ZeroTier。先做：

```
TUN ↓ Pump ↓ SOCK_DGRAM ↓ Mihomo
```

Pump 暂时：所有 IPv4/IPv6 packet → socketpair

### M0 验证清单

1. HTTP/HTTPS
2. DNS
3. UDP
4. IPv6
5. 大包
6. 长时间运行
7. Android 锁屏/解锁
8. VPN 重启
9. 网络从 Wi-Fi → 5G → Wi-Fi

### 实验意义

> 一旦 M0 稳定，你已经证明自己可以在不修改 Mihomo 的情况下"截获并重新分发"FlClash 的全部 TUN 流量。
> 之后 ZeroTier 只是增加一个出口。

## 五、MTU 压力测试（M0 最值得测的不是"能不能启动"，而是 MTU）

现状：

- TUN MTU = 9000
- socketpair SOCK_DGRAM：需要关注最大 datagram size、写端缓冲、超过 MTU 后的行为
- 理论判断：MTU 9000 < socket buffer ~212KB，问题不大 —— **但应直接压力测试，而不是继续理论分析**

### 测试矩阵

| MTU | 测试项 |
|-----|--------|
| 1500 | iperf3、HTTP download、UDP、ping -M do |
| 2000 | 同上 |
| 4000 | 同上 |
| 9000 | 同上 |

### 关注点

- EMSGSIZE
- packet drop
- fragmentation 异常
- gVisor panic
- throughput 明显下降

## 六、ZeroTier Android 实现方式（关键发现）

ZeroTier Core 本身不需要知道 Android TUN：

```
ZeroTier Core
      │
      │ VirtualNetworkConfigCallback
      ▼
Android Backend（官方实现）
      │
      ▼
VpnService TUN
```

**推论**：不用把 ZeroTier Core 改造成 Android VPN，可以直接：

```
ZeroTier Core
      │
      │ VirtualNetworkConfigCallback
      ▼
FlClashTier Pump
      │
      ▼
Android TUN
```

这就是非常标准的 adapter 模式。

## 七、FlClashTier 核心组件定义（最终）

```
┌─────────────────────────────┐
│         FlClashTier         │
│                             │
│  ┌─────────┐   ┌─────────┐  │
│  │ Mihomo  │   │ ZeroTier│  │
│  │ Core    │   │ Core    │  │
│  └────┬────┘   └────┬────┘  │
│       │             │       │
│       │  VirtualNet │       │
│       │             │       │
│       └──────┬──────┘       │
│              │              │
│         Packet Pump         │
│              │              │
│              └──────┬───────┘
│                     │
│              Android TUN    │
└─────────────────────────────┘
```

| 组件 | 改动程度 |
|------|----------|
| Mihomo Core | **不用改** |
| ZeroTier Core | **尽量不用改** |
| Android VpnService | **基本不用改** |
| Packet Pump | **FlClashTier 真正新增的核心** |

> 尽量不动两个成熟系统，只在它们之间增加一个很薄的适配层。
> 如果最终代码能控制在这个范围内，FlClashTier 就不是一个"魔改 Mihomo"的项目，而是一个相当干净的 **Mihomo + ZeroTier multiplexer**。

## 八、路线图

### M1（ZeroTier 接入）

```
M0:  packet ↓ pump ↓ Mihomo

M1:  packet ↓ pump
              ├── ZT route → ZeroTier
              └── other   → Mihomo

反向: ZeroTier frame ↓ pump ↓ TUN
```

- 先硬编码 `192.168.191.0/24`，不做 Managed Routes 动态同步
- 第一个目标：`Ubuntu 192.168.191.1 │ ZeroTier │ Android 192.168.191.100` **ping 通**
- 这一个测试的价值非常大

### M2

- 防环 + 自动 Managed Routes（不硬编码网段，ZT core 的 managed routes 自动进 Pump 路由表）

### 优先级结论

> 项目最值得先做的不是 M1，而是把 **M0 做得极其扎实**。
> M0 一旦证明稳定，后面 ZeroTier 的加入已经不是"能不能实现"的问题，而只是"怎么把第二个出口接进来"的工程问题。

## 九、风险与坑（讨论中确认）

- **stack 锁 gvisor**：FlClash 默认 gvisor；system 栈虽也纯 read/write，但 gvisor 用户态栈对 MTU/行为更可控
- **ZT 控制流量防环**：不要自己维护 IP/端口白名单。复用 ZeroTier Android 官方实现 — core 暴露 VirtualNetworkConfigCallback 帧回调，底层物理 socket 用 VpnService.protect(socket) 绕过 TUN（否则 ZT UDP → TUN → pump → ZT → … 环路）
- **DNS 分流**：mihomo TUN 模式 dns-hijack 会吞 DNS 查询；ZT 内网用主机名访问会解析失败，用 IP 最稳
- **ZT managed route 若配 0.0.0.0/0** 会饿死 mihomo，Pump 要处理路由优先级或给警告
- **未验证项（M0 要回答的）**：Android + gVisor + socketpair + Mihomo 在实际高并发网络下是否完全等价于 TUN —— 用 MTU 压力测试回答
- **GitHub clone 超时**（GnuTLS recv error）：用 `https://codeload.github.com/<owner>/<repo>/tar.gz/refs/heads/<branch>` 或 goproxy.cn module zip 更稳
